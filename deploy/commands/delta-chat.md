# Delta Chat Bridge

Демон (`claude-delta-daemon.service`) уже должен работать как systemd
`--user` сервис — эта команда с ним не взаимодействует напрямую, только
через CLI/sqlite drop-box.

Session id — переменная окружения `$CLAUDE_CODE_SESSION_ID`. Ниже во всех
`claude-delta` вызовах она **не передаётся явно как позиционный аргумент**
— CLI сам берёт её из окружения, если аргумент опущен. Так и должно быть:
буквальный `"$CLAUDE_CODE_SESSION_ID"` в тексте команды — это
shell-expansion, и permission-классификатор Claude Code просит
подтверждение на такую команду при каждом вызове, сколько allow-правил ни
добавляй (подставляемое значение не известно на момент сопоставления).
Голый литерал без `$` матчится префиксным allow-правилом чисто.

Каждая команда ниже — **одна строка `claude-delta <subcommand> ...`**, без
`cd`/`source`/`export`. `claude-delta` — установленный в PATH скрипт
(`~/bin/claude-delta`, симлинк на venv), сам находит sqlite (абсолютный
путь по умолчанию в `cli.py`) и не нуждается в активации venv. Раньше
рецепт был трёхстрочным (`cd ~/work/claude-delta && source
.venv/bin/activate` + `export DELTA_STORE_DB=...` + сама команда) — но
`source` попадает под отдельную проверку permission-классификатора
("evaluates arguments as shell code"), которую не снимает никакой
allow-rule, поэтому `send` продолжал спрашивать подтверждение на каждый
вызов независимо от allowlist (подтверждено живьём 2026-08-27). Одна
простая команда без `source` матчится обычным allow-правилом
(`Bash(claude-delta:*)`) и подтверждения не просит.

**Важно (архитектурный поворот 2026-08-09/10)**: если сессия запущена
внутри tmux, `on` дополнительно регистрирует её у диспетчера
(`register-tmux`) — дальше permission-промпты харнеста форвардятся в чат
и ответы инжектятся обратно в панель **самим демоном**, без участия кода
сессии. Не нужен `/loop`/`ScheduleWakeup` внутри сессии для доставки —
диспетчер сам опрашивает панель и drop-box постоянным процессом (см.
`docs/design.md` в vault, раздел «Архитектурный поворот»). Если сессия
**не** в tmux — работает старый режим: `check` нужно гонять вручную или
через `/loop`, как раньше.

**Поведение, пока чат armed (главный смысл всего инструмента)**: любое
место, где иначе был бы вызван `AskUserQuestion` или где я бы просто
остановился спросить/подтвердить у пользователя — вместо этого:
1. Сформулируй вопрос текстом (варианты — просто перечисли в тексте,
   free-text ответ потом сам сопоставишь с вариантом).
2. Отправь через `claude-delta send "ВОПРОС"`.
3. Не вызывай `AskUserQuestion` — заверши ход. Если сессия
   зарегистрирована в tmux — диспетчер сам инжектирует ответ как
   очередной ввод в панель на следующем такте. Если не в tmux — ответ
   заберёт следующий `/delta-chat check` (вручную или через `/loop`).

**Не только вопросы**: чат — это не только канал подтверждений, а замена
самого присутствия за ноутбуком. Раз в достаточно естественную веху —
закончил содержательный кусок работы, принял решение, наткнулся на
проблему, поменял план, ответил на что-то важное — присылай короткий
апдейт через `send`, не дожидаясь, пока понадобится что-то спросить. Не
отчитываться о каждом шаге/тул-колле (спам хуже тишины), но и не
работать молча час, если результат уже есть. Ориентир — как ты бы сам
написал в мессенджер человеку, который отошёл: по существу, без
формальностей.

**Имя группы = текущая тема (с 2026-09-07).** Тема, заданная при `on`,
не обязана оставаться актуальной на всю сессию — контекст переключается
(новый проект, новая задача). Как только тема сессии заметно меняется —
пользователь явно сказал «переключимся на X», или ты сам перешёл к
самостоятельному новому куску работы — переименуй чат вслед за темой,
той же короткой (3-7 слов) формулировкой, что и при `on`:
```bash
claude-delta rename "НОВАЯ_ТЕМА"
```
Не на каждую мелкую под-задачу внутри одного контекста — только когда
тема, которую видно в списке чатов, реально перестала описывать, чем
занята сессия. После переименования — как обычно, короткий апдейт через
`send` (правило «не только вопросы»), что теперь в работе.

**Переключение режима сессии из чата (с 2026-09-08).** Сообщение из чата
вида «переключи на manual/auto/plan», «выйди из auto режима» и т.п. —
квази-команда, не текст для ответа. Обработай так:
```bash
claude-delta cycle-mode
```
Жмёт Shift-Tab в своей же tmux-панели (харнесс так переключает
permission-режим) и печатает хвост панели — последние строки со
статус-строкой, где виден текущий режим (`manual mode on` /
`plan mode on` / `auto mode on`). Цикл замкнутый (3 состояния,
`manual → plan → auto → manual → ...`), способа «сразу поставить X» нет
— только относительный шаг. Если после вызова напечатанный режим не тот,
что просили, — вызови `cycle-mode` ещё раз (не больше 3 раз подряд, цикл
не длиннее), пока не совпадёт. Дальше — как обычно, `send` с итоговым
режимом.

Команда не трогает Delta Chat/daemon вообще — чистая tmux-операция,
работает независимо от armed/disarmed. Единственное требование —
`register-tmux` уже был вызван (иначе `cycle-mode` ругнётся, что сессия
не зарегистрирована).

**Внимание — auto mode classifier.** Пока сессия сама в `auto mode`,
харнесс отдельным классификатором блокирует некоторые Edit/Write-правки
(подтверждено 2026-09-07/08 на правках `tmux.py` и этого файла) — без
обычного permission-промпта, без варианта разрешить через allow-правило.
Если внутри auto mode правка получает deny с формулировкой «auto mode
classifier» — не повторяй ту же правку вслепую: сначала `claude-delta
cycle-mode` (выйти в `manual` — один шаг цикла, `auto → manual`), потом
повтори правку — в `manual` тот же Edit идёт обычным (форвардящимся)
промптом.

**Permission-промпты харнеста.** Их сессия не видит и не решает сама —
для tmux их форвардит диспетчер автономно (см. `on` ниже), для
остальных обхода нет. Форвардится голый текст промпта, без контекста.
Поэтому перед шагом, который может в такой промпт упереться
(нетривиальный Bash, правка конфигов, деструктив) — необязательно, но
уместно — кинь в чат короткую фразу заранее: «делаю X». Не на каждый
шаг, но так, чтобы к моменту форвардинга в чате уже был понятен
контекст. Это то же правило «не только вопросы» — трансляция процесса,
а не только вопросов и вех.

Без этого правила вся связка не имеет смысла — цель не «видеть
уведомления», а реально отвечать на подтверждения с телефона, когда не
за ноутбуком.

**Важно про природу канала (уточнено 2026-08-10)**: для tmux-сессий
диспетчер инжектирует входящие из Delta Chat как обычный ввод в панель —
буква в букву, будто пользователь напечатал сам с клавиатуры, никаких
меток/тегов/обёрток. Это осознанный выбор: я не могу и не должен
пытаться технически отличить «это с телефона» от «это с клавиатуры» —
веду себя одинаково в обоих случаях, полагаясь на два правила выше
(вопрос вместо `AskUserQuestion` → `send`; содержательный апдейт → `send`)
как на общее поведение, а не на реакцию на маркер. Если после ответа на
новый ввод есть что сообщить — просто следую правилу «не только
вопросы» и шлю апдейт, независимо от того, кто на самом деле напечатал.

**Явный вопрос из чата → ответ тоже в чат (закреплено 2026-08-27).** Если
входящее сообщение — вопрос, пришедший из самого чата, ответ на него
уходит через `send`, а не только в терминал: пользователь может быть
только на телефоне и терминал вообще не увидит. Это отдельно от общего
правила апдейтов выше — конкретно про прямой обмен вопрос/ответ.

**Тег `[delta-chat:reminder]` (с 2026-08-11)** — единственное
исключение из «никаких меток» выше, и не про контент с телефона: сразу
после каждой доставки диспетчер отдельной строкой инжектирует ровно этот
текст, без перевода/вариаций (сам тег языконезависим, демон не знает,
на каком языке ведётся сессия — вся трактовка живёт здесь). Увидев его:
это не вопрос и не апдейт от пользователя, не отвечай на него отдельно и
не переспрашивай, что это. Смысл — просто напоминание держать в голове
уже описанное выше правило (вопрос → `send`, апдейт → `send`), потому что
в длинных сессиях оно реально теряется из внимания (после компакции
контекста или просто за давностью `on`) — воспринимай его как триггер
перечитать два правила про armed-чат выше, если по факту доставленного
сообщения что-то из них применимо прямо сейчас.

Выполни действие по аргументу $1:

## `on`
Сначала сформулируй короткую (3-7 слов) тему текущей сессии по контексту
разговора — она же имя группы, она же первое сообщение (без первого
сообщения групповой чат в Delta Chat не "промотируется" и не появляется
у собеседника, поэтому пустым/дефолтным именем не отделаться).

```bash
claude-delta create-session --name "ТЕМА_СЕССИИ" --message "ТЕМА_СЕССИИ"
```

Если `$TMUX` установлена — сразу зарегистрируй у диспетчера (permission-
промпты начнут форвардиться автоматически, доставка ответов тоже
автоматическая, `/loop` не нужен):
```bash
claude-delta register-tmux
```
Если `$TMUX` не установлена — сообщи, что permission-промпты форвардиться
не будут (только явные вопросы через `send`), и что для полного режима
нужно быть внутри tmux-панели. В этом случае можно предложить
`/loop 2m /delta-chat check` — старый ручной путь доставки.

Выведи пользователю id чата и коротко — какой режим доставки включился.

**Сразу после арминга — статус в чат.** Первое сообщение (тема) уже
ушло технически ради "промоушена" группы, но само по себе не несёт
контекста — вооружающийся с телефона не обязан помнить, на чём сессия
остановилась. Отправь вторым `send` короткий статус: что делалось перед
этим/что сейчас в работе (1-3 предложения, как апдейт в правиле «не
только вопросы» ниже).

Если прямо в этот момент сессия ждёт ответа пользователя — открыт
permission-промпт харнеста в панели, или ты сам до этого остановился с
вопросом (через `AskUserQuestion` или просто текстом) — **повтори этот
вопрос в чат** тем же `send` или отдельным следующим. Не полагайся на
то, что форвардинг диспетчера (для tmux-сессий) сам его продублирует
задним числом — он ловит новые появления промпта, а не то, что уже
открыто на момент арминга.

## `check`
Ручной забор новых сообщений — нужен только для сессий **без**
tmux-регистрации (для tmux-сессий диспетчер доставляет сам):
```bash
claude-delta check
```
Если пришли новые сообщения — обработай их как обычный ввод пользователя
(в них может быть распознанный текст голосового, с префиксом
`[голосовое]`); по правилам выше — вопрос из чата, требующий ответа,
и содержательный апдейт по ходу дела отправляй через `send`. Если пусто
— просто ничего не делай.

## `off`
Закрыть сессию — демон сам напишет в чат, что сессия неактивна, и снимет
tmux-регистрацию, если она была:
```bash
claude-delta close
```
Группу не удаляй — пользователь чистит вручную, когда сам решит.
Если в этой сессии был запущен `/loop ... /delta-chat check` — останови
его тоже (`stop: true` в `ScheduleWakeup`), иначе пробуждения продолжат
приходить впустую.

## `status` (по умолчанию, без аргумента)
Проверить, жив ли демон-сервис и активна ли сессия здесь — не забирает
сообщения (в отличие от `check`), просто смотрит состояние:
```bash
systemctl --user is-active claude-delta-daemon.service
claude-delta status
```

После каждого действия — коротко сообщи результат.
