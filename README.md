# claude-delta

Мост между сессией [Claude Code](https://claude.com/claude-code) и [Delta Chat](https://delta.chat)
для двусторонней связи с оператором вне терминала.

Идея: под каждую сессию — отдельная группа в Delta Chat, удаляется по
завершении. Claude пишет туда только то, что требует внимания; вопросы, требующие
подтверждения от человека, уходят в чат, ответ возвращается в сессию.

Delta Chat выбран как транспорт вместо, например, Telegram Bot API, потому что
работает поверх обычного IMAP/SMTP — не зависит от инфраструктуры одной
площадки, которая может быть недоступна в отдельных сетях/регионах без
дополнительного туннелирования.

> Статус: ядро моста (демон + CLI) реализовано и проверено вживую —
> создание сессионного чата, отправка, приём текста и голосовых. Skill
> `/delta-standby` (arm/disarm внутри сессии Claude Code) и systemd-юнит
> для демона — ещё нет.

## Механизм обратной связи

Рассматривались общие паттерны получения ответа во внешнем асинхронном
канале, независимо от транспорта:

1. Блокирующий поллинг в одном вызове — простой, но ограничен по времени ожидания.
2. **Асинхронные пробуждения** — сессия шлёт вопрос, засыпает, периодически
   просыпается проверить, не пришёл ли ответ. Выбран как основной.
3. Push/webhook-driven resume — требует публичного endpoint, не входит в MVP.
4. Fire-and-forget уведомление + человек сам возвращается к сессии — без
   диалога внутри чата.
5. Drop-box — общее хранилище между каналом и сессией, разделяет "как канал
   получает ответ" и "как сессия его видит". Используется как обвязка над (2).
6. Агент как часть самого чата — архитектурно другая модель (сессия и есть
   чат), не рассматривается здесь.

Итоговая схема: **2 + 5**. Отдельный демон держит соединение с почтовым
ящиком бота, пишет входящие сообщения в drop-box; сессия по расписанию
проверяет drop-box и продолжает работу, когда там появляется ответ.

## Приём сообщений

Ядро — `deltachat-rpc-server` (обёртка над `deltachat-core`, Rust): у него
уже есть собственный IMAP-планировщик с реконнектом, переизобретать
raw IMAP IDLE вручную не нужно.

Поверх — independent-страховка на нашей стороне:

- fallback-поллинг раз в 10 минут (на случай, если ядро тихо потеряло
  соединение и не заметило)
- переиздание IDLE не реже раза в ~25 минут (протокольный лимит — 29 мин,
  RFC 2177)

## Управление сессией

Планируется как arm/disarm-команда, вызываемая явно внутри сессии:

**on:**
1. Поднять демон-мост, если не запущен
2. Создать/переиспользовать групповой чат под сессию
3. Зарегистрировать `session-id ↔ chat-id` в drop-box
4. Заблокировать засыпание хоста на время ожидания (с потолком по времени —
   на случай, если сессия упадёт, не вызвав `off`)
5. Запустить цикл пробуждений, проверяющий drop-box

**off:**
1. Снять блокировку сна
2. Пометить запись в drop-box закрытой
3. Демон-мост не останавливать — общий для всех сессий

## Реализация

Демон (`claude_delta.daemon`) — единственный процесс, которому разрешено
держать открытым соединение с Delta Chat. CLI (`claude_delta.cli`) и
будущая сессия говорят только с общим sqlite drop-box
(`claude_delta.store`) — так исключается конфликт двух процессов за один
account db.

```
claude-delta create-session <session_id> [--name NAME]   # -> chat_id
claude-delta send <session_id> <text>
claude-delta check <session_id>                          # новые сообщения, JSON lines
claude-delta close <session_id>
```

Голосовые сообщения распознаются локально через `faster-whisper` (модель
`small`, CPU, без PyTorch/облака) — см. `claude_delta.stt`. Текст приходит
с префиксом `[голосовое]`.

Демон запускается переменными окружения `DELTA_ADDR`, `DELTA_PASSWORD`,
`DELTA_PEER_ADDR`, `DELTA_ACCOUNTS_DIR`, `DELTA_STORE_DB`:

```
DELTA_ADDR=bot@example.org DELTA_PASSWORD=... DELTA_PEER_ADDR=me@example.org \
  python -m claude_delta.daemon
```

## Конфигурация

Секреты (адрес и пароль ящика бота) не хранятся в репозитории — только в
переменных окружения при запуске демона.
