# Установка claude-delta на новом хосте

Это раннбук для Claude Code-агента, которого попросили развернуть мост
`claude-delta` (Delta Chat ↔ Claude Code) на текущей машине. Ссылку на
этот файл пользователь даёт отдельной сессии — начни с чтения целиком,
затем следуй разделам по порядку. Не пропускай раздел «Вопросы
пользователю» — без ответов на них дальнейшие шаги делать нельзя.

Итог установки: работающий systemd `--user` демон + локальный skill
`/delta-chat`, готовые к `/delta-chat on` в любой tmux-сессии Claude Code
на этой машине.

## 0. Быстрая проверка — уже стоит?

```bash
systemctl --user is-active claude-delta-daemon.service 2>/dev/null
ls -la ~/.claude/commands/delta-chat.md 2>/dev/null
```

Если сервис уже `active` и симлинк уже на `~/work/claude-delta/deploy/commands/delta-chat.md`
— установка не нужна, сообщи об этом и остановись (не переустанавливай
поверх рабочего деплоя без явной просьбы).

## 1. Предпосылки (проверь и сообщи, если чего-то нет)

- `python3 --version` — нужен ≥ 3.11.
- `which tmux sqlite3` — оба нужны (tmux — для диспетчера, sqlite3 — для
  ручной диагностики drop-box). Имя **пакета** для установки зависит от
  дистрибутива и не всегда совпадает с именем бинарника — на Fedora
  пакет называется `sqlite`, бинарник всё равно `sqlite3` (на
  Debian/Ubuntu пакет и называется `sqlite3`). Проверяй по `which`, а не
  по названию пакета в голове.
- `systemctl --user status` — работает (у пользователя есть DBus-сессия).
- Исходящий доступ к IMAP/SMTP (порты 993 и 465) для того провайдера,
  который выберут под ящик бота — не проверяй заранее, это проявится
  само на шаге 5 (в логе демона).
- **Важно**: юнит демона (`deploy/claude-delta-daemon.service`) сделан
  `WantedBy=default.target` и **без** `loginctl enable-linger` —
  осознанное решение апстрима: открытая пользовательская сессия — это и
  есть предпосылка для того, чтобы ей можно было удалённо управлять через
  Delta Chat. Если у этого хоста нет постоянной вошедшей сессии (сервер
  без графики/автологина), демон будет падать при выходе из сессии —
  спроси пользователя, актуально ли это здесь (см. вопрос 3 ниже), не
  включай `enable-linger` сам без явного запроса.

Если чего-то из обязательного нет (python/tmux/sqlite3/systemd --user) —
не устанавливай пакеты сам без подтверждения, спроси, можно ли.

## 2. Вопросы пользователю (задать ДО любых изменений)

Используй `AskUserQuestion` (или обычным текстом, если пользователь его
уже отклонял в этой сессии) — три развилки:

**a. Ящик бота.** Нужен отдельный email с IMAP/SMTP-доступом
(app-password, не основной пароль аккаунта) — это НЕ то же самое, что
ящик, уже используемый ботом на другом хосте (см.
`~/obsidian_vault/02 Projects/Delta Bridge/creds.md` — если этот vault
доступен на текущей машине, прочитай для контекста, но не бери значения
оттуда как есть, они принадлежат другому хосту). Варианты:
  - Отдельный новый ящик под этот хост (по умолчанию/рекомендуется —
    независимый демон без риска конфликта IMAP-сессий, отдельные чаты в
    Delta Chat на телефоне — видно, с какого хоста прилетело).
  - Тот же ящик, что на другом хосте — предупреди, что два демона на
    одном аккаунте одновременно не тестировались (в README прямо
    сказано: демон — единственный процесс, которому разрешено держать
    открытым соединение с аккаунтом), и уточни, точно ли пользователь
    этого хочет.
  Дальше в этом файле предполагается, что выбран отдельный ящик —
  пользователю нужно завести его вручную (шаг 3) и передать тебе адрес +
  app-password.

**b. Куда положить креды.** Предложи два способа передать
`DELTA_ADDR`/`DELTA_PASSWORD`:
  - Пользователь сам добавляет секцию в
    `~/obsidian_vault/02 Projects/Delta Bridge/creds.md` (шифруется
    git-crypt) и говорит «готово» — предпочтительно, если vault на этой
    машине есть.
  - Пользователь диктует значения прямо в чат сессии — годится, если
    vault недоступен; в этом случае после установки сам предложи занести
    их в creds.md при следующей синхронизации vault.

**c. Постоянство сессии.** Спроси, есть ли на этом хосте открытая
пользовательская сессия, которая будет жить постоянно (десктоп с
автологином, всегда открытый терминал и т.п.), или это headless-сервер —
от ответа зависит, предупреждать ли пользователя, что демон будет
падать при разлогине (см. п.1), и не нужно ли `enable-linger` как
осознанное исключение из дизайна.

Не продолжай к шагу 3, пока не получишь ответы на все три.

## 3. Ручные действия пользователя (не автоматизируются)

Сообщи пользователю явным списком, что нужно сделать руками, и жди
подтверждения/значений:

1. Завести отдельный почтовый ящик под бота (провайдер — на усмотрение
   пользователя; на omni055 использован Yandex, там app-password
   создаётся в настройках аккаунта → «Пароли приложений»). Delta Chat
   не требует ничего специфичного от провайдера, кроме обычного
   IMAP/SMTP-доступа.
2. Сгенерировать app-password для этого ящика (не основной пароль
   почты).
3. Передать тебе одним сообщением, нумерованным списком, чтобы ничего не
   потерялось:
   1. адрес ящика бота;
   2. app-password (не основной пароль);
   3. IMAP/SMTP хост:порт — **только** если провайдер не входит во
      встроенную базу автоконфига deltachat-core (Yandex и mail.ru
      проверены, работают без явных host:port; для прочих уточни явно).
4. **Прислать secure-join ссылку/QR** — без неё бот не сможет создавать
   чаты (`peer_contact()` требует уже известный key-contact). В Delta
   Chat на телефоне: своя учётка → «Пригласить друзей» / «Add contact»
   → показать QR или скопировать ссылку вида
   `https://i.delta.chat/#FINGERPRINT&v=3&i=...&s=...&a=...&n=...` —
   присылают текстом, распознаётся по префиксу `https://i.delta.chat/#`
   или `OPENPGP4FPR:`. Надёжнее обычного письма (см. шаг 4а) — обходит
   спам-фильтры, проверено 2026-08-11 на смене ящика omni055.

   **`DELTA_PEER_ADDR` отдельно спрашивать не нужно** — он уже есть в
   этой же ссылке параметром `a=` (`parse_peer_addr()` в
   `scripts/securejoin.py` его вытаскивает; тот же приём одной строкой:
   `python3 -c "from urllib.parse import parse_qs; print(parse_qs('<ссылка>'.split('#',1)[1])['a'][0])"`).
   Получаешь ссылку — сразу знаешь и её, и peer-адрес.

## 4. Установка (выполняешь сам после получения кредов)

```bash
# 4.1 Клонировать, либо, если уже клонировано (в т.ч. в этой же сессии
# раньше или прошлой установкой) — git pull, не клонировать поверх:
if [ -d ~/work/claude-delta/.git ]; then
  git -C ~/work/claude-delta pull
else
  git clone https://github.com/andrey-n-safonov/claude-delta.git ~/work/claude-delta
fi
cd ~/work/claude-delta

# 4.2 Виртуальное окружение
python3 -m venv .venv
source .venv/bin/activate
pip install -e .
deactivate
```

Проверь, что `deltachat-rpc-server` встал как готовый бинарник (пакет
тащит прекомпилированный wheel под linux x86_64/arm64) — если pip падает
на сборке из исходников, это сигнал незнакомой архитектуры/платформы,
остановись и сообщи пользователю, не пытайся чинить сборку Rust-ядра
руками.

```bash
# 4.3 Конфиг демона
mkdir -p ~/.config/claude-delta
cp deploy/daemon.env.example ~/.config/claude-delta/daemon.env
# отредактировать daemon.env: DELTA_ADDR, DELTA_PASSWORD — из шага 3.
# DELTA_PEER_ADDR — не спрашивать пользователя, взять параметром `a=`
# из secure-join ссылки (см. шаг 3, п.4).
# (DELTA_ACCOUNTS_DIR и DELTA_STORE_DB уже указывают на ~/work/claude-delta/…,
#  трогать не нужно, если не просили другой путь)
chmod 600 ~/.config/claude-delta/daemon.env

# 4.4 systemd --user юнит
mkdir -p ~/.config/systemd/user
ln -sf ~/work/claude-delta/deploy/claude-delta-daemon.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now claude-delta-daemon.service

# 4.5 Skill /delta-chat — симлинк на версионированный файл в репо
ln -sf ~/work/claude-delta/deploy/commands/delta-chat.md ~/.claude/commands/delta-chat.md
```

Правь `daemon.env` через `Edit`/`Write`-инструменты, не через `sed` вслепую
— значения содержат пароль, лучше явно увидеть итоговый файл (без вывода
пароля в чат) перед `chmod`.

## 4а. Bootstrap peer key-contact (обязательно для нового ящика)

Свежесконфигурированный аккаунт бота не знает пользователя — `bridge.py`
(`peer_contact()`) явно требует уже обменянный ключ, иначе
`create_session_group()` падает с «нет известного key-contact». Нужно
один раз (на каждый новый ящик бота) провести secure-join:

```bash
systemctl --user stop claude-delta-daemon.service   # аккаунт эксклюзивно нужен скрипту

cd ~/work/claude-delta && source .venv/bin/activate
export DELTA_ACCOUNTS_DIR="$HOME/work/claude-delta/accounts"
python scripts/securejoin.py '<ссылка, которую прислал пользователь>'
deactivate

systemctl --user start claude-delta-daemon.service
```

`DELTA_PEER_ADDR` можно не экспортировать — скрипт сам разбирает `a=` из
той же ссылки и печатает результат; переменная нужна только если хочешь
явно свериться (несовпадение скрипт подсветит сам).

Ждёт до 60с подтверждения (`progress=1000`), в конце печатает результат
`get_contact_by_addr` — контакт должен быть найден (не `None`). Если
таймаут — не паникуй сразу: проверь `get_contact_by_addr` в выводе
скрипта всё равно (Autocrypt-обмен иногда проходит без формального
завершения хендшейка, см. `docs/design.md` в vault, инцидент
2026-08-08); если и там `None` — проверь спам-папку почты бота и попроси
пользователя переслать ссылку ещё раз.

## 5. Проверка

```bash
# Логи демона — ждём успешного логина в Delta Chat, без ошибок IMAP/SMTP.
# С 2026-08-11 демон сам логирует итог connectivity после start_io()
# ("connectivity после start_io(): подключён" или похожее) — отдельный
# smoke-test для этого не нужен.
journalctl --user -u claude-delta-daemon.service -n 40 --no-pager
```

Если демон не поднялся — не трогай ничего в самом Delta Chat аккаунте
пользователя (не удаляй чаты/письма), просто покажи лог и спроси, как
продолжать.

**Не запускай `scripts/smoke_test.py` параллельно с работающим демоном**
— оба открывают один и тот же account db эксклюзивно
(`accounts.lock file is already locked`). Он нужен только для
самого первого логина ДО первого старта демона (см. шаг 4а — тот же
принцип, `securejoin.py` тоже требует демон остановленным); если демон
уже поднят и в логе нет ошибок — отдельно перепроверять смысла нет.

Живой функциональный тест — без входа с телефона, через CLI напрямую
(что реально проверяет создание чата end-to-end, не только логин):
```bash
cd ~/work/claude-delta && source .venv/bin/activate
export DELTA_STORE_DB="$HOME/work/claude-delta/bridge.sqlite3"
SID="install-test-$(date +%s)"
python -m claude_delta.cli create-session "$SID" --name "Тест установки" --message "Тест установки, можно игнорировать"
sleep 3
python -m claude_delta.cli close "$SID"
deactivate
```
Проверь `journalctl` на «создан чат id=…» и «outbox … отправлен» без
ошибок, и попроси пользователя подтвердить, что сообщение дошло на
телефон. Если есть открытая tmux-сессия Claude Code на этой машине —
дополнительно можно проверить `/delta-chat on` / `/delta-chat off`.

## 6. После установки

- Сообщи пользователю итог: адрес ящика бота на этом хосте, статус
  сервиса, что диспетчер работает.
- Если креды передавались устно (не через vault) — предложи занести их в
  `~/obsidian_vault/02 Projects/Delta Bridge/creds.md` новой секцией
  («Ящик бота — <имя хоста>»), при следующем `git pull`/`push` vault.
- Если это первая установка на дополнительном хосте — предложи обновить
  `~/obsidian_vault/02 Projects/Delta Bridge/CLAUDE.md` (карта проекта):
  упомянуть, что демон теперь работает на нескольких хостах, с каким
  ящиком на каждом.
- Запись в журнал (`Delta Bridge.md` в vault, если ведётся) — по
  обычному ритуалу завершения задачи.

## Откат / удаление

Если понадобится снести установку на хосте:

```bash
systemctl --user disable --now claude-delta-daemon.service
rm ~/.config/systemd/user/claude-delta-daemon.service
rm ~/.claude/commands/delta-chat.md
rm -rf ~/work/claude-delta   # сотрёт accounts/ и bridge.sqlite3 — необратимо
rm ~/.config/claude-delta/daemon.env
```

Спроси подтверждение перед `rm -rf` — это удаляет локальное состояние
Delta Chat аккаунта бота безвозвратно (сам email-ящик и переписка на
сервере провайдера не затрагиваются).
